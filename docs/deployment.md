# Next 发布与部署

Next 单应用沿用 `ghcr.io/saarjoye/mrs-core` 镜像名，替代旧版 Core/Web 双容器。**不是旧 Core 的接口兼容更新：旧 Web 依赖 3010 控制接口，不能继续搭配新版镜像。**

## 发布和切换

现有仓库的 `main` 分支通过 `.github/workflows/docker-image.yml` 构建。先执行离线测试、类型检查、ESLint、构建和 Compose 校验，再构建 `linux/amd64` 与 `linux/arm64` 候选镜像。候选镜像使用空数据、禁用外部网络做启动健康检查；成功后才更新 `5.0.0-next.29` 与 `latest`。完整提交固定标签为 `sha-<完整提交号>`。

## next.29 搜索滚动容错、报告下载与 App 故障隔离

### 搜索与下载

搜索提交后的可选滚动采用独立 10 秒预算。普通滚动错误或超时只记录安全错误分类，
关闭异常页面并跳过该页结果点击，保留配置的搜索间隔，再读取官方进度判断完成、
继续或待复核。已提交搜索不会自动重发，取消和业务日期变化仍传播，迟到操作不能
继续滚动或点击。本版不修改搜索间隔、随机滚动及结果访问配置。

“下载脱敏报告”启用时使用真实链接，修复点击后没有请求的问题；禁用或加载时
仍渲染原生按钮，不保留可导航链接。报告接口和脱敏规则保持原行为。

### App 读取与后续任务

App Dashboard 使用账号独立的有界只读恢复。授权会话最多执行一次 OAuth 获取或恢复，
更新后的令牌供发现、验证和提交共用；只有有效官方余额确认后才持久化。
同一账号客户端连续三次 401 后停止 App 请求；只有官方有效余额读取成功后才清零连续失败计数。
401 的只读重试分别等待 10 秒、20 秒，释放失败响应后再等待，授权恢复和退避均计入 45 秒总预算。
HTTP 拒绝保留传输连接，网络失败才重建；奖励提交仍为单次发送，不自动切换通道重放。
App Dashboard 读取失败只将 App 数据源标记为不可用，继续发现和执行已验证的网页任务；
未取得 App 官方状态的任务仍保留未知或待复核状态。
授权获取失败记为 `app-oauth`，授权获取后读取失败记为 `app-dashboard`。
关闭 App 活动、每日签到和阅读赚取三项后，不再获取 App OAuth 或读取 App Dashboard；
移动搜索仍使用独立的网页登录与认证槽。

阅读续跑对既有提交进行只读复核时，401、503 或网络异常保留待复核证据并返回部分完成，
后续搜索、领取和最终结算继续执行。缺少 App 授权也仅降级 App 阶段。
取消和业务日期变化仍会停止流程，迟到成功不能确认任务；临时授权页和网络响应统一清理。

`latest`。升级无需新增配置、迁移或依赖安装；保留原 Compose、持久卷、主密钥、

本版离线验收为 68 个文件、925 项测试，类型检查、Lint 和服务端/前端构建通过；
新增搜索滚动回归覆盖异常、超时、提交次数、取消、跨日、页面清理和迟到操作。
LXC 候选通过禁网且不挂载生产卷的 20 项回归、237 个构建文件校验、75 个服务端
JS 语法检查和 11 个 UI 静态资源校验，持久化配置保持一致。
实际续跑仍存在部分完成和待复核；本版不保证 App 官方接口永久恢复、所有任务完成或
未确认积分到账。GitHub Actions 的 Compose 校验、双架构构建与空数据健康检查

边界和不明确归因不会产生分类分数，不使用预计奖励或账号剩余增加补齐金额。
分类差额只用于通知展示，完整核算依据见 [通知文档](run-notifications-points.md)。

## next.26 任务包续跑、日常点击与清晰积分明细（历史版本）

网页和账号通知以“任务类别／积分／状态”展示摘要，展开保留逐项来源与证据。

发布前离线回归及 LXC 服务健康检查通过；真实日常卡片完成、积分到账和后续解锁

## next.22 首页领取修复与升级

本版包含：

- 首页 Star 奖励卡片的积分上限不再被当作可领取金额；只有明确的可领取金额
  才能参与首页领取汇总。上限卡片缺失金额时保持未知，不点击或推断领取量。
- 领取回执后每次只读复核都重新加载官方 Dashboard；明确读到零才确认完成。
  刷新失败、跳转或控件缺失保持待复核，不自动重复领取。

同时保留 next.21 已发布的兼容修复：

- 首页领取控件的中英文识别、局部金额证据和慢加载只读等待；未知积分不记为零，
  禁用控件或非官方来源不点击，提交后未确认不重发。
- 认证入口的有界 commit 导航、主文档失败分类、超时与取消清理；普通密码和已有
  Session 恢复路径保留。新版通行密钥页只做被动识别与严格官方方式返回，不包含
  自动取消 WebAuthn、伪造认证或自动处理 MFA 的实验。
- 任务卡片按官方身份及目的地约束匹配，区分找不到、来源/类型冲突和仍未完成；

- 同一官方任务的多来源观察选择整条权威记录，避免混合来源、类型和进度；SQLite
  只在同一不可变任务身份内刷新派生分类，保留历史、任务键和 mutation 账本。

应用镜像为 `ghcr.io/saarjoye/mrs-core:5.0.0-next.22`。只有 GitHub Actions 的
候选验证与提升步骤成功后，该版本及 `latest` 才可用于升级；代码推送成功不等于
镜像已发布。多架构构建仍使用锁定的依赖和 Patchright 1.61.1 浏览器层。

## LXC 本地源码独立部署

`compose.lxc.yaml` 是独立的本地源码部署入口，不与默认拉取发布镜像的
`compose.yaml` 合并。默认管理端口仍为 `8788`，容器使用非 root 的 `node` 用户、
`init`、512 MB 共享内存和独立持久卷，不使用 `privileged`。

- 先确认 LXC 内 Docker Engine、Compose 与 Buildx 均可用。保留已有可用的 Docker；
  缺少 Buildx 时只补装对应发行版插件，不为了构建替换正在使用的引擎。
- 使用新的部署目录，只传应用源码、构建清单及 Docker 配置。不复制源码机的 `.env`、
  `lxc106/`、账号数据、会话、密钥、日志、备份或 `node_modules/`。
- 创建部署专用的 `.env`，可设置 `IMAGE_TAG`、`APP_VERSION`、`WEB_BIND_IP` 和
  `WEB_PORT`。管理员变量仅用于首次引导，并应使用独立强密码，不能复用 SSH 密码。
- 首次初始化独立主密钥后保留它；不得在升级时重建或覆盖。

首次创建密钥（部署目录中以 root 执行；只适用于尚无主密钥的新安装）：

```sh
install -d -m 0700 secrets
test ! -e secrets/rewards_master_key
(umask 077; head -c 32 /dev/urandom > secrets/rewards_master_key)
chown 1000:1000 secrets/rewards_master_key
chmod 0400 secrets/rewards_master_key
```

浏览器基础层使用 Debian 官方源的 HTTPS 地址，保留 TLS 证书校验。精简 Node 镜像
的系统 CA 包通过 Node 自带的可信根证书临时引导安装，引导文件和配置随后删除。

浏览器基础层将 npm 安装、系统 CA、浏览器依赖与 Chromium 下载分为独立缓存层。apt 下载失败
最多重试两次，临时重试配置在依赖安装成功后移除；后续浏览器下载失败不会导致
已完成的系统依赖重新下载。

应用编译后使用已有 npm 缓存离线重新安装生产依赖，替代目标环境中长时间未完成的
`npm prune`。最终编译与生产依赖准备层禁止联网，不执行安装脚本，也不修改依赖版本或
锁文件。该步骤跳过在线审计以保持离线；不能将镜像构建成功视为依赖安全审计通过，
导入真实账号前应单独检查生产依赖告警，依赖升级需另行确认。

构建浏览器基础层与应用：

## 首页领取与部分完成排查

- “必应 Star 奖励”等卡片同时包含“待领取”和“积分上限”时，上限不作为可领取金额。
  只有该卡片明确标注的可领取金额才是金额证据；否则保持未知，不影响另一个已明确
  正值的首页领取汇总，也不会点击上限卡片。缺失金额不得按上限领取或当作零。

- 首页领取使用按钮或官方站内链接的可见文字、`aria-label`、`title`，以及最多三层的单控制近邻
  “可领取/待领取”金额。页面总余额不作为可领取金额，缺失、冲突或格式异常保持未知。
- 支持原生按钮、`role="button"` 和官方 Dashboard/Earn 站内链接。主页链接只打开领取面板，
  面板内的待领取金额必须与主页一致，才会点击唯一可用的“领取积分”按钮；若打开面板时
  已观察到官方 POST，则不再二次点击，转为只读复核。
- 领取汇总展开后，可以选择唯一的无数字“领取全部”
  动作；已展开的汇总不会再次点击收起，存在 `aria-controls` 时仅在指定面板查找。
- 金额为明确正整数且领取动作唯一、可见、可用时才提交。多个独立领取按钮不会相加
  或猜测目标，隐藏、禁用、兑换按钮和非官方 Rewards 页面不会作为领取入口。
- 点击不等于领取成功。动作仍经过原有 mutation 账本、服务端回执和只读金额复核；
  提交后结果不确定进入 `verification-pending`，不会自动重复领取。
- 领取后的每次金额复核都会只读重新加载官方 Dashboard，而不是反复读取提交前的旧
  页面。服务端动作回执不会自动更新页面；旧正值不能据此判定领取失败，旧零值也不能
  据此判定成功。只在新页面明确读到零时确认完成；加载失败、重定向或控件缺失仍待复核。
  已有 pending 领取也使用上述只读刷新，不解除账本保护、不重新提交领取。
- 一轮运行结束不等于所有账号或任务成功。认证导航超时且未读到余额时，积分应视为
  未知而非确认的零分；任务 `skipped` 要区分配置禁用、未发现任务与不可执行原因。
- 回归测试使用合成控件、DOM 树和响应，不登录或领取真实账号。其他服务机的截图
  不能用于确认本机运行失败；发布、重启和真实账号验收需分别确认，并保留持久卷
  与独立主密钥。保留调度时，还应核对下次执行时间，避免部署验收与定时任务重叠。

## 登录导航与慢加载容错

- 当前源码对认证入口主文档尚未提交的首次导航超时，先关闭失败的浏览器槽，短暂等待后
  用独立槽最多重试一次。第二次仍超时就保持失败；DNS/TLS 错误、页面已提交、密码提交
  后的状态和奖励 mutation 均不因此重试，避免重复提交。该恢复不等于重新执行整轮任务。
- 桌面、移动端、Bing 会话恢复与 App OAuth 的认证入口等待导航 `commit`，
  再由登录状态机观察可见控件；不再因 `domcontentloaded` 延迟直接跳过整个账号。
  单次导航仍最多 30 秒，登录流程保持 120 秒整体预算，不使用无限等待。
- 导航超时与网络失败分别记录为 `login-navigation-timeout` 和
  `login-navigation-error`，仅保留来源和路径，不记录原始异常中的查询参数或认证材料。
  网络故障不会被当成登录成功；Session 仍需 Rewards/Bing 验证后才保存。
- 未开始认证交互的未知登录页最多进行一次恢复导航；发送账号或密码后不再刷新登录入口。
  同一账号/密码步骤提交后只观察状态变化，不连续重填或重发。仅在没有可用主按钮、
  尚未点击时才使用 Enter 提交，点击结果不确定时不会再用 Enter 重试。
- 首页和展开领取面板最多追加 10 次只读控件快照、间隔 500 毫秒，等待慢加载控件。
  明确零值立即保留为零；等不到有效证据仍是未知。等待和提交前重新检查官方来源，
  取消时停止后续动作；只读重查不等于再次发送领取请求。
- 上述是源码及合成回归修复，不代表目标服务机的真实账号已经恢复。发布、容器重启、
  真实登录及领取仍需当次确认。不得通过永久代理、禁用 TLS、删除会话/数据卷或重装 Docker
  掩盖网络或账号问题；既有调度、账号、数据卷和独立主密钥保持不变。

## 账号删除

当前源码的“账号管理”可在确认后删除账号配置与三个加密认证槽。运行中拒绝删除；
删除后剩余账号的运行选择编号会重排，历史运行、任务和积分证据仍保留原账号身份与
原编号，当前任务列表不再显示已删除账号。删除不可撤销，既有备份及历史日志不会
随账号操作自动清除；需要清理备份时应另按保留策略处理。首次升级会幂等创建
`deleted_accounts` 表（Schema 6），只保存已删除账号的持久 ID 和删除时间，用于
区分旧版遗留历史与主动删除的账号。回退旧版会忽略此标记，可能再次显示旧历史账号。
